# Configuration guide

Start with [the filesystem walkthrough](getting-started.md). Choose cloud storage only when you need it and can qualify its permissions, durability and recovery behavior. The Obsidian plugin always uses **CouchDB** as its remote type, regardless of backend storage.

## Required versus optional

The server needs a TOML config, private persistent storage and one running process. **Docker, Compose, Kubernetes and Kustomize are not application requirements.** Choose an existing approved runtime; deployment examples do not define a mandatory stack.

| Location | When used | Contains |
|---|---|---|
| Ignored `config/local.toml` | All runtime routes, or another explicitly selected TOML path | Non-secret server/storage settings copied from a canonical template |
| Ignored `.env` | Only the optional Compose example | Project/port/mount paths; cloud credential **file paths**, never their values |
| Private secret files / client credential store | Selected cloud backend or device authentication | Credentials accessible only to their intended operator/service; mounted read-only when containerized |

No secrets belong in Git, images, assistant context, command arguments or logs. `.gitignore` protects `.env` variants, `config/local.toml`, `secrets/` and `data/`; it does not erase tracked history or stop an agent reading a file. Keep canonical examples generic and do not inspect existing private files by default.

## Native executable settings

Pass `--config /absolute/config.toml`, set `SYNC_CONFIG`, or use the executable's `/etc/obsidian-sync/config.toml` default. For an ordinary test, explicitly select the ignored local copy.

Use `listen = "127.0.0.1:8080"`, absolute host paths for `metadata_dir` and filesystem `root`, and a non-root service user with private directory ownership. TOML does not expand environment variables or `~`. Container `/data` paths and UID/GID 65532 are example-specific, not native prerequisites. No `.env`, Docker daemon or orchestrator is needed.

## Optional Compose settings: host side

```dotenv
COMPOSE_PROJECT_NAME=obsidian-sync-demo
SYNC_PORT=8080
SYNC_DATA_DIR=./data
SYNC_CONFIG_FILE=./config/local.toml
```

- **Project:** choose a unique, approved name and use it consistently for all operations.
- **Port:** Compose maps `127.0.0.1:SYNC_PORT` to container port 8080. Changing the host port does not require changing the container's `listen` setting.
- **Data path:** a new private backend directory, not an Obsidian vault folder. It contains authoritative metadata and, for filesystem mode, immutable blobs.
- **Config path:** the selected local template copy, mounted read-only as `/etc/obsidian-sync/config.toml`.

The service receives `SYNC_CONFIG=/etc/obsidian-sync/config.toml`; this is distinct from host-side `SYNC_CONFIG_FILE`. Do not feed these container `/data` paths to a native server accidentally.

For these container mounts, UID/GID **65532** must be able to write the data directory and read the config. Do not run the server as root or make it world-writable. Reuse exactly those mounts for offline administration.

## TOML settings: inside the server

The filesystem template below uses container paths/listening. Native execution changes those to its approved host paths and loopback listener; the other server settings are the same:

```toml
listen = "0.0.0.0:8080"
metadata_dir = "/data/metadata"
max_blob_bytes = 268435456
vault_quota_bytes = 10737418240
max_inflight = 4
operation_timeout_secs = 300
job_quota_per_vault = 100
job_max_attempts = 5

[http]
allowed_origins = ["app://obsidian.md", "capacitor://localhost", "http://localhost"]

[storage]
kind = "filesystem"
root = "/data/blobs"
```

| Setting | Template value | Meaning |
|---|---:|---|
| `listen` | `0.0.0.0:8080` | Container listener; host exposure remains loopback in Compose |
| `metadata_dir` | `/data/metadata` | Local POSIX SQLite and persistent writer authority, in every storage mode |
| `storage.root` | `/data/blobs` | Filesystem objects, generated by the server rather than named by note paths |
| `max_blob_bytes` | 256 MiB | Individual storage-object bound, not a promise that a client can upload a 256 MiB note/request |
| `vault_quota_bytes` | 10 GiB | Retained allocation per vault; archives/orphans/history also consume it |
| `max_inflight` | 4 | Concurrent storage work; review spool/memory budgets before changing |
| `operation_timeout_secs` | 300 | Storage/job operation deadline |
| `job_quota_per_vault` / `job_max_attempts` | 100 / 5 | Persistent integrity-job quota and bounded retry attempts |

Defaults when omitted from `[http]`: 16 MiB request/response, 1 MiB canonical document, 128 documents per batch, eight active request slots, 6,000 requests/minute per principal, burst 256 and 20-second long-poll. Additional admission/JSON/connection bounds still apply. The templates explicitly supply the Obsidian origins; an omitted origin list defaults empty.

Use normal client batches of 25 with a modest queue first. A larger blob limit does not enlarge HTTP/document/structural budgets. Unknown TOML fields, invalid ranges and files over 64 KiB are rejected. Exact supported fields and bounds are implemented in `src/config.rs`; this is not arbitrary CouchDB configuration.

### CORS and private HTTPS

Add only exact origins needed by your clients. No wildcard, embedded credentials, remote plaintext origin or path-prefixed origin. CORS is not authentication and should not be relaxed to fix a wrong token or vault grant.

Keep Basic/Bearer credentials on loopback for same-host experiments or approved private HTTPS for remote clients. A reverse proxy must expose the server at its root URL, not an unstripped path prefix. Private TLS, ACLs and device access are operator controls; configuration alone does not turn them on.

## Choose a storage backend

All modes retain **the same local metadata directory**, one writer and an installation-exclusive blob namespace. Changing `kind` is not a data migration: do not point an existing database at an empty provider/prefix. Stop and obtain a migration/recovery plan for existing data.

| Backend | Start from | Additional preparation |
|---|---|---|
| Filesystem | [filesystem.toml](../config/filesystem.toml) | Private local POSIX data directory; simplest first setup |
| S3 / MinIO | [s3.toml](../config/s3.toml) | Dedicated bucket/prefix, HTTPS endpoint/region/addressing style, conditional-write support and mounted keys |
| Native GCS | [gcs.toml](../config/gcs.toml) | Dedicated bucket/prefix, scoped service-account file and native provider tests |
| Native Azure | [azure.toml](../config/azure.toml) | Dedicated container/prefix, expiring HTTPS-only container SAS and native provider tests |

For S3, the repository supplies [docker-compose.s3.yml](../docker-compose.s3.yml). Choose the S3 template as `config/local.toml`, then set **file paths**, not values, in ignored `.env`:

```dotenv
S3_ACCESS_KEY_FILE=./secrets/s3-access-key
S3_SECRET_KEY_FILE=./secrets/s3-secret-key
```

With approved private files readable by the service:

```sh
docker compose -f docker-compose.yml -f docker-compose.s3.yml config --quiet
```

Use that same `-f` file set for provision/start/stop/admin commands. A successful render does not probe IAM or publish objects. Remote plaintext S3, redirects and credentials embedded in URLs are not a supported workaround. `prefix` is a nonempty installation identifier using letters/digits/hyphen/underscore, not an arbitrary slash-separated path.

The repository does **not** supply GCS/Azure Compose overlays. A native process can receive the documented credential-file environment variables directly. For containers, supply reviewed read-only secret mounts using your chosen runner; [Kustomize overlays](../deploy/kustomize/overlays) are optional examples, not a reason to require Kubernetes. Do not invent filenames or silently deploy to the current kube-context.

Provider secret interfaces are `GCS_SERVICE_ACCOUNT_FILE` and `AZURE_SAS_TOKEN_FILE`. Azure requires a dedicated expiring HTTPS-only container SAS with `sr=c` and exactly `sp=rcwd`; its staging-delete authority does not make final objects immutable against a stolen key. S3 temporary session tokens and workload/managed-identity refresh are not implemented. Rotate mounted provider credentials through an approved restart.

Before provider use, read [the storage contract](storage.md) and [operator guidance](operations.md#storage-modes). Startup/`verify-storage` probes create retained objects. Never test a real account without explicit authorization. RustFS tests are not AWS/MinIO/GCS/Azure certification; GCS/Azure acceptance still needs native disposable-provider tests. Lifecycle cleanup applies only to staging, never final blobs.

## Validate and change settings safely

For a native source build:

```sh
./target/release/obsidian-sync-server --config config/local.toml check-config
```

For the optional Compose example, with its image built:

```sh
docker compose config --quiet
docker compose run --rm --no-deps server check-config
```

`config --quiet` only checks Compose rendering. The server's `check-config` parses TOML without opening SQLite/storage in either route. Neither proves TLS, provider support, replication or backups. For ordinary admin/configuration changes, stop the writer first and follow [operations](operations.md); restart only that approved server instance, then verify readiness and synthetic client behavior.

Keep an encrypted copy of configuration with the matched metadata/blob backup and protect recovery secrets separately. Never delete `writer.lock`, edit SQLite or prune immutable objects to fix an error. See [troubleshooting](getting-started.md#if-something-fails) and [backup/restore](operations.md#persistent-state-backup-and-tested-restoration).
